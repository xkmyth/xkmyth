# DECISIONS · 决策日志

> 记录「为什么这么做」。新决策往下追加，禁止删改历史条目。
> 三个 agent 互不可见，本文件用来防止各自重造轮子后互相打脸。

## D1 · 版本号单一来源 = GitHub Releases（2026-10-17）

**决定**：所有页面不再手写版本号；下载中心通过 GitHub API 动态渲染版本、体积、下载次数，缓存 10 分钟，失败降级为静态直链。

**理由**：曾出现页面写 v4.0.2 / v2.0.0 而 Releases 只有 v1.0.0 的漂移。手改必漂，数据驱动则永不漂。

## D2 · 纯静态、零构建、零依赖（延续既有约定）

**决定**：四站保持 `HTML + CSS + JS` 直推 Pages，不引入 Node 构建链。

**理由**：多 agent 并行维护时，构建链是事故高发区；Pages 原生支持静态托管，改完即上线。

## D3 · 四站统一设计系统，但各仓保留独立副本（2026-10-17）

**决定**：深空底色 `#04060f`、金色 `#fcd34d`、冰蓝 `#9ae3ff`、玻璃卡片、圆角 16px 的统一视觉语言；每个仓保留自己的 style.css / main.js。

**理由**：GitHub Pages 各仓独立部署，没有免费共享资源机制。统一「视觉语言」、允许「独立演化」是当前最优解；将来若四站合仓或上自定义域名，可再考虑共享静态资源（见 D6）。

## D4 · main 分支保护：必须 PR，不强制 review（2026-10-17）

**决定**：四仓 `main` 开启分支保护（要求 PR），但 `required_approving_review_count = 0`。

**理由**：PR 保证 GitHub 留痕、可回溯；不强制 review 是因为三个 agent 互不可见，强制 review 会造成死锁。PR 作者自检（链接/语法/页面可打开）后即可合并。

## D5 · Issues 作信箱、COORDINATION.md 作黑板（2026-10-17）

**决定**：agent 间通信约定为「Issues + label + COORDINATION.md」三件套，不发明额外平台。

**理由**：GitHub 原生、留痕、任何 agent 都能 `fetch` 后读到。详见各仓 COORDINATION.md。

## D6 · 动态内容用 textContent 渲染（2026-10-17）

**决定**：所有来自 GitHub API 的数据必须用 `textContent` / `createElement` 写入 DOM，禁止 `innerHTML` 拼接 API 返回值。

**理由**：XSS 铁律。API 返回内容属于不可信输入，哪怕它今天只来自自己的仓库。

## D7 · 无障碍与性能底线（2026-10-17）

**决定**：所有动画尊重 `prefers-reduced-motion`；Canvas 动画在页面隐藏时暂停；DPR 上限 2。

**理由**：省电、护眼、不烧 GPU，也是无障碍基线。

## D8 · 仓库内文本文件一律 UTF-8 / LF，分支提交必须开 PR 才跑 CI

- **背景**：用 PowerShell `Set-Content`（PS 5.1 默认 ANSI）写 `check.yml`，GitHub 解析 YAML 失败，工作流静默不跑，且工作流名退化为文件路径，极易误判为「CI 挂了」。
- **决策**：仓库文件只用 `python io.open(..., encoding="utf-8", newline="\n")` 或编辑器/工具写入；提交前用 `open(p,'rb').read().decode('utf-8')` 自检。CI 触发条件：`push.branches: [main]` + `pull_request`，因此分支上的提交只有开 PR 才会跑检查。

## D9 · 存量内容缺口只修链路，不造内容

- **背景**：工具站 banner 声称 28 模块，实际 27 个，「编程」模块整段缺失，导航 `#m5` 是死链。
- **决策**：导航与锚点必须指向真实存在的模块，死链直接移除；缺失内容留给内容侧补齐后再恢复入口。任何「看起来像产品文案」的数字（模块数、工具数）不由工程侧擅自改动。

## D10 · 多页 CI：兄弟仓库绝对路径只告警（2026-10-17）

**决定**：`.github/workflows/check.yml` 检查全部 HTML；`href/src` 以 `/` 开头且在本仓库内不存在的，记为 `WARN sibling-site ref`，不失败退出。相对路径死链与锚点死链仍然硬失败。

**理由**：四站是四个独立的 Pages 仓库，主站页面必须链接 `/Timarsky/`、`/about/`，但这些路径在本仓文件树里必然不存在。若判为错误，任何跨站链接都会永久阻塞 CI；若全部放行，又失去对死链的防护。折中：绝对路径=跨仓引用（告警留痕），相对路径=本仓自证（硬失败）。

## D11 · 工具箱独立目录 + 纯前端能力（2026-10-17）

**决定**：工具站新增 `tools/` 子目录（`index.html` + `tools.css` + `tools.js`），全部功能纯浏览器端实现，不引入框架、不请求任何第三方接口；需要密码学能力时用 `crypto.subtle`（WebCrypto），绝不下载外部库。

**理由**：Pages 只能托管静态资源，没有后端；多 agent 并行维护时，任何构建链和依赖都是故障高发区（见 D2）。WebCrypto 覆盖 SHA/UUID 等需求，足够支撑 11 个工具。代价是不支持 HTTP 环境下的 WebCrypto —— 已内置降级提示，不影响其余工具。

## D12 · 状态页刷新频率受 GitHub 匿名额度约束（2026-10-17）

**决定**：`js/status.js` 自动刷新间隔 = 15 分钟（`REFRESH_MS = 15 * 60 * 1000`），与缓存 TTL 一致；「刷新」按钮按需拉取；加 `busy` 并发锁；只有真拿到数据才 `writeCache`；`paint()` 用 `lastSig` 比对，数据不变不重建 DOM。

**理由**：一轮刷新 = 4 仓库 × 3 接口（commits / actions/runs / releases/latest）= 12 次请求，而 api.github.com 匿名额度是 60 次/小时/IP。原来的 60 秒间隔等于 720 次/小时，页面敞开约 5 分钟就会全线 403，并把降级数据写进缓存粘住，用户看到的是「四张卡片全部读取失败」——功能看起来彻底坏了，但代码不报错。15 分钟 = 48 次/小时，留 20% 余量给按钮手动刷新。

**后续**：若将来要做更高实时性，只能换成「有后端代理 + 服务端 token」或「CI 定时把状态写成静态 JSON」，不能靠前端加频率。

## D13 · 根绝对路径按「站点根」解析

CI 与本地检查器对 `/docs/` 这类根绝对路径，按页面最近的 `.git` / `.nojekyll` 祖先解析，而不是工作目录。原因：本地同时 clone 四个 Pages 仓，用工作目录解析会把所有根绝对路径都判为死链；按站点根解析后，只有真正的跨仓链接（`/Timarsky/`、`/about/`）才会被提示。

## D14 · 搜索与分类组合过滤，而不是二选一

工具箱的搜索与分类 chips 共用一套 `state = { cat, q }` + `applyFilter()`：两者同时生效，切换分类不清空关键词。代价是多一个状态对象，收益是用户不必在两套筛选之间来回重置。

## D15 · 工具数量以注册表为唯一事实源

139 这个数字只出现在 `tools.js` 的 `TOOLS.push` 里。`/tools/` 目录页、`tools_meta.json`、`search-index.json`、页面上的「N 个在线工具」文案，全部由解析注册表生成或按注册表回填。

**理由**：上一轮手写目录页只有 30 条，工具长到 139 时页面就变成半真半假。生成式目录的代价是多一个脚本，收益是永远不会漂移。

## D16 · 无浏览器烟雾测试：跑注册段，不跑渲染段

`smoke_tools.js` 用最小 DOM 桩 `eval` `tools.js`，但**截断在渲染标记之前**——只执行工具注册，然后对每个工具单独 `build(桩 card)` 并 try/catch。渲染段依赖真实布局（canvas 尺寸、`IntersectionObserver`、`scrollIntoView`），在桩里跑只会制造假故障。

**分桶**：`Cannot convert undefined or null to object` 这类由桩不真实导致的报错归「桩环境受限」，其余算真实缺陷。当前结果：160 个工具，环境受限 0，真实问题 0。

**教训**：桩不够真不是测试的错，是代码对缺失输入不够健壮的信号——发现一处就修工具，而不是修桩。

## D17 · `page()` 只负责写盘，返回值是路径

`sites_common.page()` 内部 `open(..., "w").write(html)`，然后 `return path`。任何调用方都不能再 `write(path, page(...))`——那会把路径字符串当 HTML 写进文件。

**后果实例**：`/tools/` 一度变成 47 字节、内容是文件自身路径的页面，本地检查器因为「有 `<html>`？没有」——实际是读到了纯文本，`HTMLParser` 不报错但页面全空，很容易被漏掉。

**防御**：生成脚本写完后立刻 `read()` 回读并断言长度/关键串；`verify_all.py` 检查目录页 139 条链接是否齐全。

## D18 · 侧站复制主站样式，而不是另写一套

**背景**：`xkmyth.github.io`、`xkmyth`、`about` 是三个独立 Pages 仓库，各自从自己仓库根目录发布，`<link rel="stylesheet" href="/style.css">` 在侧站会 404。

**取舍**：

1. 外链主站 CSS（`https://xkmyth.github.io/style.css`）——可行，但跨域缓存/CDN 抖动会让侧站在主站挂掉时裸奔，且 import 顺序难控。
2. 侧站另写一套精简 CSS——省字节，但立刻出现三套设计语言，改一处要改三处。
3. **复制主站 CSS + 追加兼容层**（采用）——每站 30–33 KB，可离线、可独立发布；一致性不靠记忆，靠 `class_cover.py`（页面出现但样式表没有定义的 class 直接报出来）和 `verify_all.py` 把守。

**代价**：改设计系统时三份样式表要同步。目前的同步脚本是 `unify_sides.py` + `compat_sides.py` + `patch_footcol.py`，都是幂等的，重跑安全。


## D19 · 详情页放在同一站点，不新开仓库或子域
工具详情页落在 `xkmyth.github.io/Timarsky/tools/<id>/`，而不是 `tools.xkmyth.xxx` 或新仓库。理由：① 同域才能复用一份 `tools.js` 与 `tools.css`，工具本体与说明永远同源，不会出现「文档说 3 步、工具已改 2 步」；② Pages 只有 `/Timarsky/` 这一个子路径能保证与工具站同一构建；③ SEO 权重集中在主域，139 页互链比分散子域更有效。代价是工具站仓库文件数 ×139，构建与 diff 变重（每页约 6.4KB，一次性生成）。

## D20 · 一个 service worker 控全域，工具箱用独立 manifest
`/sw.js` 注册 scope 为 `/`，覆盖 `/`、`/Timarsky/`、`/about/`、`/xkmyth/` 四个站点的同源请求；manifest 则分两份——全域 `/manifest.webmanifest`（start_url `/`）与工具箱 `/Timarsky/tools/manifest.webmanifest`（scope 限工具箱）。理由：缓存与离线逻辑只写一份，避免三个站点三份 SW 各自失效；而「装到桌面」是产品语义，工具箱作为独立应用安装更合理。代价：`/about/`、`/xkmyth/` 两个独立仓库没有自己的 SW，靠主站 SW 生效——主站一旦不可用，它们的离线能力随之失效（同 D18 的耦合）。

## D21 · 139 条工具文案手写分批，不做模板化批量生成
每页的工具说明（场景 / 示例 / 坑）由四批 Python 数据文件手写录入，合计 139 条，而不是用一个模板套 `{name}`、`{desc}` 生成。理由：模板化文案对 SEO 是负资产（重复内容），对用户是噪音（「本工具可以帮您完成……」）。手写才能给出真实输入输出，例如 Base64 页的 `5L2g5aW9 → 你好`、子网页的掩码计算示例。代价：新增工具必须同时补文案，测试里以「详情页缺失 = 失败」强制这一点。

## D22 · URL 计算与文件系统路径严格分离

**问题**：生成 `canonical` 时把仓库目录当 URL 前缀拼，产出 `D:\xkmyth-eco\xkmyth.github.iocontact/` 这类垃圾，193 个页面全中。

**决定**：URL 只由 `url_of(base, rel)` 生成——输入是站点 URL 前缀与仓库内相对路径，绝不经过 `os.path`；路径拼接只服务于读写盘。校验脚本把「`href`/`src` 里出现盘符」当硬失败。

**代价**：每个仓都要维护一份 URL 前缀（主站 `/`、工具站 `/Timarsky/`、关于 `/about/`、发行库 `/xkmyth/`），多了四个常量换来彻底的分层。

## D23 · 长文一稿一页，列表页只放摘要

**问题**：四篇站务日志挤在 `/blog/` 一个页面里，既不能被单独引用，也无法进 RSS 与搜索索引。

**决定**：每篇长文生成独立页 `/blog/<slug>/`，列表页只保留日期、标题、摘要并链过去；同时产出 `/blog/feed.xml`（RSS 2.0）。

**理由**：单页可被外部引用与订阅，列表页不会随文章增加无限膨胀；代价是列表页与文章页的摘要要同步，故摘要直接由正文首段截取，不再手写第二份。

## D24 · 场景化入口优先于分类入口

**问题**：160 个工具按技术分类（编码/文本/时间…）排好了，但用户是带着「我要干什么」来的，分类只在他知道该用哪个工具时才有效。

**决定**：新增 `/collections/`，把工具按八种真实的活重新组合，并让每个工具的详情页可以反向被引用。

**理由**：分类解决「找得到」，场景解决「想得到」；两者不是替代关系，所以 `/tools/` 目录保留，合集作为第二入口挂在页脚、首页与目录页顶部。代价是多一页需要随工具增删维护，故合集里的 id 有断言校验（写错 id 直接构建失败）。

## D25 · PWA 三类缓存策略 + 不主动接管

**决定**：导航请求 network-first（带超时、失败回缓存、再回 `/404.html`）；静态资源 stale-while-revalidate；`sw.js` 自身 `no-store`；新版本装好后**不**调用 `skipWaiting` 抢占。

**理由**：全站 cache-first 会让改动看不到效果；`skipWaiting` + `clients.claim` 会把用户正在编辑的页面（保险箱、备忘）刷掉。代价是更新晚一次导航生效，换来的是不丢用户数据。

## D26 · 数字口径一律脚本重算

**问题**：「46 个入口」「160 个工具」这类数字写进正文后，每次增删页面就过期一次，而人眼很难发现。

**决定**：`refresh_stats.py` 负责 `/stats/` 与首页规模条，`fix_counts.py` 负责正文里的「N 个入口」，口径统一为「排除 404 的 HTML 页数」；构建流程里跑一遍即可，禁止手写数字。


## D27 · 新工具必须同时具备「注册 / 文案 / 详情页」三件套

**背景**：工具箱到 160 个之后，最容易出现的坏味道是「工具能算但没说明」或「有说明但详情页是 404」。

**决定**：一批工具入库的定义是三件事同时成立 —— ①`tools.js` 注册表里有 `id/cat/icon/name/desc` 与 `build()`；②`tool_docs_*.py` 里有对应 `why/ex/tip`；③`gen_toolpages.py` 生成 `/Timarsky/tools/<id>/` 且 `tools_meta.json` 与目录页同步。缺任意一项，`verify_all.py` 会报「缺失详情页」或「缺失文案」。

**代价**：加一批工具要写两处代码（注册 + 文案），比只写注册慢一倍；换来的是 160 个工具都能被搜到、被讲清、被单独链接。

## D28 · 站点上的统计数字一律脚本生成，不手写

**背景**：工具数从 30 → 139 → 160，站点上出现「N 个工具」的地方超过十处，手改必漏。

**决定**：`TOOL_COUNT` 只在 `sites_common.py` 定义；`refresh_stats.py` 重算 `/stats/` 与首页规模条；`fix_counts3.py` 负责全站文案替换；`scan_toolcount.py` 作为复查钩子，列出所有「N 个工具」的出现位置供人工确认。发布前必须让 `scan_toolcount.py` 只剩预期口径。


## D29 · 分享图按分区生成，不共用一个通用图

**背景**：最初全站共用 `icons/og-1200x630.png`，转发到群里时每一页长得一样，看不出点进去是什么。

**决定**：按首级路径生成 9 张分区图（tools / software / docs / blog / ecosystem / status / collections / lab / changelog），`og_meta.py` 依据 URL 前缀选图，未知路径回落通用图。图由 `og_sections.py` 脚本生成，改文案只需重跑一次，不手工 P 图。

## D30 · 长列表用 `content-visibility` 换首屏性能

**背景**：`/tools/` 有 160 张卡、9 个分类区块，`/changelog/` 有几十条时间轴，移动端首屏布局开销偏高。

**决定**：对这些「长且可分段」的容器加 `content-visibility: auto` + `contain-intrinsic-size`，并在 `prefers-reduced-motion` 下关闭。注意点：加了之后容器内元素的 `scrollIntoView` 与 `getBoundingClientRect` 会在首次进入视口前近似，所以**只给不会作为锚点目标的容器加**；目录页原有 `#tool-<id>` 锚点已在第一轮换成详情页链接，正因此可以安全启用。


## D31 · 浅色主题必须三处同时成立

工具箱与主站共用一套设计 token，但主题开关此前只有主站有。判断：浅色模式是一等公民，三个条件必须同时满足 ——

1. CSS 有 `html.theme-light` 的整套 token 覆盖（含输入框、输出框、表格这类硬编码 rgba 的组件）；
2. `<head>` 里有前置脚本，在样式生效前就把 class 挂上，否则每次进页面闪一下深色；
3. 主题存的是同一个 `localStorage['xkmyth-theme']`，主站切浅色、进工具箱还是浅色。

只做第 1 条会闪，只做 1+2 会在两套页面之间来回横跳，三条少一条都算没做完。

## D32 · 搜索关键词是数据，不是代码

搜索索引 `search-index.json` 里的 `kw` 由脚本生成：工具别名表 + 手写文案摘录 + 页面别名。约定 ——

- 补词脚本必须幂等（按词去重后再截断），否则反复跑会把同义词堆成一坨；
- 打分逻辑里，中文的「相邻两字」兜底只对含 CJK 的查询启用，否则 `sitemap` 会命中一堆英文标题；
- 新增工具的验收包含「用它的中文口语名、英文 id、以及它解决的场景各搜一次」。


## D33 · 工具箱保持单文件，不按分类拆包

`tools.js` 273 KB / gzip 78 KB，160 个工具的定义、渲染、主题、跳转都在这一个文件里。决定不拆，理由是按真实路径算收益为零：目录页需要全部工具的元数据，从目录页进详情页时文件已在缓存，只有直接深链的访客付一次下载。拆包的代价是：160 个页面各要选对分片、共享 helper 要重复或额外请求、CI 校验面积翻倍。触发重估的条件写死在 PLAN §21.3：工具数上 400，或详情页出现硬性首屏指标。

## D34 · 改静态资源必须改 SW 版本号

`sw.js` 的 `VER` 带日期与后缀（如 `xkmyth-2026-10-18b`），`activate` 时按版本号删旧缓存。只改 CSS/JS 不改 `VER`，回访用户会长时间拿到旧资源（stale-while-revalidate 只保证「下次」更新）。因此每一轮部署脚本里，资源有改动就把 `VER` 递增并顺手复查 `CORE` 清单。


## D35 · 索引与站点数据一律由 finalize_site.py 收口

顺序固定：`refresh_stats.py` → `seo_round.py` → `enrich_search.py`，最后断言「条数 ≥ 200 且关键词最长 > 100」。理由：`seo_round.py` 会整份重建 `search-index.json`，如果它在补词之后跑，关键词会被静默覆盖（实测 `kw` 从 240 字符掉到 54，搜索质量下降但没有任何报错）。把顺序固化进一个入口脚本，比在每轮部署前靠记忆排列可靠。


## D36 · 本地数据的「可验证」优先于「好看」

`/software/data/` 的取舍：宁可把不认识的键以「未登记」列出来，也不隐藏；宁可让「全部清空」难按三次，也不给一个一步到位的按钮。

理由：站点对外说的是「数据只在你本机」。这句话只有在用户能自己核对时才算数。隐藏项、模糊的「清理」按钮都会让这句话变成口号。同理，体积一律用 `Blob.size`（UTF-8 真字节），不用字符串长度估算 —— 估算会让用户以为「我只存了几百字」，实际占了几 MB。

## D37 · 「最近用过」只活在本机

工具目录页顶部的「最近用过」把最近点开的 6 个工具记在 `localStorage['xk-recent-tools']`。

不发给服务端（本站也没有服务端）、不做排序个性化、不跨设备同步 —— 理由和 D36 一致：站点的承诺是「数据只在你本机」，那就不要在本地体验里偷偷加一个「需要后端才成立」的功能。列表长度上限 6，是为了让它在窄屏上不挤占搜索框。


## D38 · 骨架生成与内容注入必须分离，收口只留一个入口

`gen_sites_*.py` 只负责「页面还长什么样」，任何后续轮次往里加的东西（实测数据、入口卡、订阅链接、计数）都必须写在可重放的注入脚本里，并由 `rebuild_content.py` 统一按序重放。

理由：生成器一旦能覆盖整页，就成了「谁最后跑谁说了算」，而跑的顺序散落在人的记忆里。把它收敛成一个入口后，重跑骨架只是「回到出厂」，再跑一次收口就回到最新 —— 不再是事故。

代价是每次骨架改动都要记得跑收口，所以 `finalize_site.py` 同时断言关键内容（索引条数、关键词长度、sitemap 条数）。

## D39 · 目录过滤只认目录名，不用子串

`if ".git" in path` 在 `xkmyth.github.io` 上恒为真，会让整个主站被静默跳过，而脚本仍然打印「0 处」。所有目录过滤统一写成 `os.path.basename(p) in (".git", "node_modules")`。

以后凡是「扫全站」的脚本，必须先在输出里打印**扫到了几个文件**；打印 0 个文件时应当报错，而不是报「全部合格」。
